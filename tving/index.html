willnew

팀 누구나 채널이나 스레드에 한 줄로 맡기면 AI가 고치고, 테스트 관문과 요청자의 시각적 전후 비교를 거쳐 개발자에게 승인 요청으로 올라오는 팀 도구. 승인 시 PR → CI → 배포까지 자동 추적되고, 요청자에게 쉬운 말로 답이 갑니다

결과맡기기부터 병합까지 약 47초 (실제 Claude Code, 1건). 요청 3건 중 2건 병합, 검증 실패 1건은 승인 차단. 스레드 협업 및 Playwright 전후 시각 비교 지원 (테스트 94개 통과)
기술TypeScript · React · Hono · Playwright · vitest
코드검증 관문 · 시각적 전후 비교 · 스레드 채팅 · PR → CI → 배포 · 요청자 답장 · E2E 테스트 · 측정 근거 · 저장소

기능

예시: 고객 문의 "1/31 가입자 다음 결제일이 3/3으로 잡혀 있대요. 2월은 말일(2/28)에, 3월엔 다시 31일이어야 하는 거 맞죠?". 인물은 가상이고 화면은 데모 모드에서 촬영

  1. 1
    누구나 채널에 맡기기 (스레드 분리)

    CS 담당자가 채널에 고객 문의를 올리면 독립된 카드 스레드가 생성됨. 계획 에이전트가 '버그 수정, 에이전트 1개, npm test로 확인'으로 정리

  2. 2
    테스트가 판정, 실패하면 한 번 더

    willnew가 npm test를 직접 돌려 종료 코드로 판정. 첫 시도는 '2월 다음 3/31 복귀' 테스트에서 실패 → 실패 로그를 붙여 재작업 → 7개 통과

  3. 3
    테스트를 고친 결과는 차단

    테스트 파일을 고쳐서 통과한 결과는 '테스트 파일 고침'으로 표시하고, 바로 승인하지 못하게 검토 화면으로 보냄

  4. 4
    요청자 시각 확인 & 상자 그려 피드백

    코드를 못 보는 요청자가 main과 변경 화면을 나란히·슬라이더로 비교. 어색한 곳에 직접 네모 상자를 그려 '다시 봐 주세요'를 누르면 같은 브랜치에서 에이전트가 이어서 수정

  5. 5
    줄 댓글로 다시 맡기기

    diff 줄에 "date-fns-tz 새로 넣지 말고 lib/time.js 써주세요"라고 남기면 에이전트가 이어서 고치고 다시 검증

  6. 6
    검토 차례 알림 → 휴대폰 승인

    통과하면 채널에서 담당 개발자를 부름("@이해준 검토 차례예요. 테스트 7개 통과, main과 충돌 없음"). 휴대폰에서 밀어서 승인

  7. 7
    승인 후 PR → CI → 배포 & 요청자 답장

    PR 생성 → CI 3개 통과 → squash 병합 → production 배포까지 실시간 추적. 배포가 끝나면 승인한 개발자 이름으로 요청자에게 쉬운 말 답장

wasnew

AI 에이전트의 파일 조작(이동·삭제·이름변경)을 저널링하고, Git이 없거나 커밋되지 않은 폴더에서도 작업 단위로 안전하게 되돌리는 실행취소(Undo) 레이어 (MCP)

결과테스트 131개 All Pass, MCP 도구 16개, 의존성 0개, 5,300건 작업 시 토큰 99.6% 절감 (1,687 토큰), 대용량 파일 되돌리기 12ms (Git 대비 약 700배 고속)
기술TypeScript · Node 20+ · MCP(stdio) · GitHub Actions(Ubuntu, Windows, macOS × Node 20, 22)
코드계획·승인·적용 · 경험 학습과 동적 신뢰 정책 · MCP 도구(16개) · 가드 훅 · 벤치마크 · 저장소

이럴 때 씁니다

  1. 1에이전트가 일반 폴더를 정리

    "다운로드 폴더 정리해 줘"라고 하면 파일을 여러 하위 폴더로 옮기고 일부는 지움. git 저장소가 아니므로 git으로는 되돌릴 수 없음

  2. 2wasnew가 저널에 안전 기록

    모든 이동마다 원래 위치, 에이전트, 모델, 사유를 저널에 남김. 삭제는 실제 지우지 않고 전용 휴지통으로 이동

    wasnew_move · wasnew_trash
  3. 3한 번에 원래대로 롤백

    결과가 마음에 안 들면 그 작업 묶음을 통째로 되돌림. 그 사이 원래 자리에 새 파일이 생겼으면 덮어쓰지 않고 보호

    wasnew undo --batch

Description

  • 배경 Claude Code 공식 문서에서도 "체크포인트는 Bash 명령어로 수정된 파일(rm, mv, cp 등)을 추적하지 않는다"고 명시함. 다운로드나 문서 폴더처럼 Git 관리를 하지 않는 곳에서 에이전트가 파일을 삭제·이동하면 복구할 방법이 없으며, 수천 개 파일 작업 시 39만 토큰에 달하는 컨텍스트 낭비가 발생함
  • 구현
    • 16개 MCP 도구 제공. 모든 변경을 `.wasnew/` 저널에 에이전트 이름, 모델, 작업 사유와 함께 기록하고 휴지통으로 안전 격리
    • Plan → Human Approve → Apply: 대량 작업이나 보호 경로(`protect`) 접근 시 위험 반경을 계산해 사람의 사전 승인을 강제 (에이전트 스스로 승인 불가)
    • 경험 학습(Lessons)과 신뢰 정책(Trust): 사용자가 되돌린(undo) 패턴을 집계하여 같은 유형의 실수를 피하도록(`avoid`) 새 에이전트 접속 시 MCP 프롬프트에 자동 주입. 취소율이 낮은 검증된 에이전트는 승인 필요 임계값을 20건에서 200건으로 자동 상향
    • 토큰 요약 압축: 5,000건 작업 결과 반환 시 요약 템플릿과 상위 샘플 20개만 반환해 컨텍스트를 보호 (39만 토큰 → 1,687 토큰)
    • Claude Code의 Bash 및 PowerShell 도구에서 `rm`, `mv`, `del` 실행을 가로채 `wasnew_trash` 사용을 유도하는 PreToolUse 가드 훅 제공
  • 검증
    • 실제 Claude Code 헤드리스 세션 연동 실측: 199개 다운로드 파일 정렬, 훅 기반 `rm -rf` 차단, 원클릭 일괄 되돌리기 E2E 검증
    • 사용자 파일을 영구 삭제하지 않음 (사람이 직접 empty-trash 할 때만 비움)
    • 테스트 131개 All Pass, CI 3개 OS(Ubuntu, Windows, macOS) × Node 20, 22 환경, 런타임 의존성 0개
  • 성과 2GB 대용량 파일(8개) 기준 이동 11ms, 언도 12ms (Git 대비 각각 약 1,000배, 700배 고속). 5,300건 대량 작업 시 토큰 소비 99.6% 절감 (394,569개 → 1,687개)
  • 한계 파일 시스템 커널 드라이버 수준이 아니므로, 에이전트가 만든 임의의 복합 셸 스크립트 내부에서의 직접 삭제는 추가 런타임 샌드박스가 필요함

    • 판정, 위치, 유사 사례는 코드가 계산하고, 로컬 LLM(Qwen3.5 4B)은 논문 근거가 있는 원인 표 안에서 원인 후보와 점검 순서만 작성
    • 모델 임베딩 거리로 처음 보는 패턴을 경고
    • 경고가 켜졌거나 확신이 낮거나 맵이 깨진 웨이퍼는 조사 에이전트로. LLM이 분류, 위치, 비슷한 웨이퍼, 이웃 로트, 원인 표 도구 중 무엇을 부를지 정하고, 판정, 새 패턴 후보, 맵 이상, 사람 확인 중 하나로 보냄
  • 검증
    • 불량 8종을 하나씩 빼고 학습해, 뺀 패턴을 가려내는지 평가, 로트 단위 분할
    • 판독 카드를 코드로 6가지 검사(판정과 위치가 계산값과 같은지, 원인이 표 안인지, 표 밖 공정 용어가 없는지 등), 걸리면 재질문
    • 에이전트가 근거로 적은 값이 실제 도구 결과와 다르면 코드가 제출을 거절. 새 패턴 후보는 이웃 로트 근거가 있어야 통과
  • 성과
    • 처음 보는 패턴 AUROC 0.55 → 0.92 (확신도 → 임베딩 kNN)
    • 같은 120장에서 판독 카드 첫 답 규칙 통과 8% → 94% (프롬프트 3차 수정). 규칙을 지킨 비율이지 원인이 맞은 비율은 아님
    • 160장 평가(파이프라인만 → 에이전트 혼합): 학습에서 뺀 패턴을 판정하지 않고 넘긴 비율 63% → 79%, 깨진 맵 20장 중 16장을 맵 이상으로 분류, 지어낸 근거 18건 거절
    • 라벨 없는 맵에서 기존 9종에 없는 줄무늬와 혼합 패턴 후보 발견
    • 나중 로트에서 성능 하락(0.963 → 0.743) 확인
  • 한계 아는 패턴 정답률은 파이프라인만 쓸 때보다 낮음(87% → 81%). 확신이 낮은 웨이퍼를 사람에게 넘긴 대가. 4B 모델이라 조사에 장당 수십 초

차체 용접 디지털 트윈 + AI 제조성 판정

신차 차체 설계안을 기존 용접 라인 로봇이 전부 용접할 수 있는지 AI로 먼저 걸러 내고, 못 하는 곳이 있으면 에이전트가 한국어 요청대로 고친 설계를 찾아 시뮬레이터로 확인하는 도구

결과설계 1만 안 탐색 약 11시간 → 4.7분. 용접 못 하는 타점 재현율 99.9% (학습에 없던 설계 200개)
기술Python · KUKA KR210 기구학 · LightGBM · Ollama(Qwen3.5 4B) 도구 호출
코드대리 모델 · 설계 수정 에이전트 · 테스트 · 저장소

Description

  • 배경 설계안 하나를 로봇 시뮬레이션으로 확인하면 판정만 약 10초, 로봇 배정까지 약 3분. 설계 1만 안을 보려면 약 11시간(3코어)
  • 구현
    • 설계 변수 10개(플랜지 폭, 첫 타점 거리 등) → 판재 15장, 스폿 용접 타점 75개 생성
    • KUKA KR210 기구학으로 타점마다 로봇이 닿는지 판정(관절 한계, 간섭, 접근 경로)
    • LightGBM 대리 모델이 같은 판정을 설계 1개당 0.05초에
  • 예시 설계안 A는 못 하는 타점 2개(S23, M00) → 플랜지만 넓힌 B도 2개 → 첫 타점 거리 80 mm, 실–B필러 간격 50 mm로 바꾼 C는 0개
  • 검증
    • 학습에 없던 설계 200개를 시뮬레이터와 대조. 첫 판 정밀도 93.4%에서 특징 계산 버그를 찾아 고친 뒤 100%
    • AI가 추천한 20안을 시뮬레이터로 다시 돌려 18안 일치, 틀린 2안은 경계 바로 옆
  • 설계 수정 에이전트
    • 「플랜지 폭은 그대로, 첫 타점 거리는 60 이하」 같은 요청을 LLM(qwen3.5 4B)이 제약으로 바꾸고, 후보 탐색 → 시뮬레이션 → 제출 도구를 불러 가장 적게 바꾼 설계를 찾음
    • 시뮬레이터가 못 하는 타점 0개를 확인한 설계만 제출 가능, 제약 위반은 코드가 거절
  • 성과
    • 1만 안 탐색 약 11시간 → 4.7분. AI는 1차 선별, 경계 근처는 시뮬레이터가 확정
    • 에이전트: 시작 설계 12개 전부 시뮬레이터 확인까지 성공, 실행당 평균 66초. 단변수 훑기만 주면 8/12였고 후보 탐색 도구를 준 뒤 12/12
  • 한계 변수 하나를 고정하면 에이전트 3/12, 전수 탐색 4/12. 제약 해석 12건 중 1건 틀림
