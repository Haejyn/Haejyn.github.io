willnew

팀 누구나 채널에 한 줄로 맡기면 AI 에이전트가 고치고, 테스트를 통과한 수정만 개발자에게 승인 요청으로 올라오는 팀 도구. 승인하면 PR → CI → 배포까지 이어지고, 요청한 사람에게 쉬운 말로 답이 갑니다

결과맡기기부터 병합까지 약 47초 (실제 Claude Code, 1건). 요청 3건 중 2건 병합, 검증 실패 1건은 승인 차단
기술TypeScript · React · Hono · vitest
코드검증 판정 · PR → CI → 배포 · 요청자 답장 · E2E 테스트 · 측정 근거 · 저장소

기능

예시: 고객 문의 "1/31 가입자 다음 결제일이 3/3으로 잡혀 있대요. 2월은 말일(2/28)에, 3월엔 다시 31일이어야 하는 거 맞죠?". 인물은 가상이고 화면은 데모 모드에서 촬영

  1. 1
    누구나 채널에 맡기기

    CS 담당자 윤서아가 고객 문의를 #cs-문의에 그대로 올림. 계획 에이전트가 '버그 수정, 에이전트 1개, npm test로 확인'으로 정리

  2. 2
    테스트가 판정, 실패하면 한 번 더

    willnew가 npm test를 직접 돌려 종료 코드로 판정. 첫 시도는 '2월 다음 3/31 복귀' 테스트에서 실패 → 실패 로그를 붙여 재작업 → 7개 통과

  3. 3
    테스트를 고친 결과는 차단

    테스트 파일을 고쳐서 통과한 결과는 '테스트 파일 고침'으로 표시하고, 바로 승인하지 못하게 검토 화면으로 보냄

  4. 4
    줄 댓글로 다시 맡기기

    diff 줄에 "date-fns-tz 새로 넣지 말고 lib/time.js 써주세요"라고 남기면 에이전트가 이어서 고치고 다시 검증

  5. 5
    검토 차례 알림 → 휴대폰 승인

    통과하면 채널에서 담당 개발자를 부름("@이해준 검토 차례예요. 테스트 7개 통과, main과 충돌 없음"). 휴대폰에서 밀어서 승인

  6. 6
    승인 후 PR → CI → 배포

    PR을 올리고 CI 3개가 통과하면 main에 병합, production 배포까지 단계마다 채널에 남김. CI가 실패하면 멈추고 실패한 항목을 알림

  7. 7
    요청한 사람에게 답장

    배포가 끝나면 승인한 개발자 이름으로 요청자에게 쉬운 말로 답함. 요청자는 '내 요청'에서 진행 상황만 봄

wasnew

AI 에이전트가 내 폴더에서 옮기고 지운 파일을, 작업 단위로 한 번에 되돌리는 도구

결과테스트 78개, MCP 도구 12개, 의존성 0개, 이동 2,625건 되돌리기 2.9초
기술TypeScript · Node 20+ · MCP(stdio) · GitHub Actions(ubuntu, windows, macOS × Node 20, 22)
코드계획, 승인, 적용 · 크래시 복구 · MCP 도구 · 저장소

이럴 때 씁니다

  1. 1에이전트가 폴더를 정리

    "다운로드 폴더 정리해 줘"라고 하면 파일을 여러 폴더로 옮기고 일부는 지움. git 저장소가 아니라 git으로는 되돌릴 수 없음

  2. 2wasnew가 전부 기록

    이동마다 원래 위치, 에이전트, 사유를 저널에 남김. 지우기는 휴지통으로 옮기기만 함

    wasnew_move · wasnew_trash
  3. 3한 번에 원래대로

    결과가 마음에 안 들면 그 작업 묶음을 통째로 되돌림. 그 사이 원래 자리에 새 파일이 생겼으면 덮어쓰지 않고 건너뜀

    wasnew undo --batch

git과 다른 점

gitwasnew
대상사람이 커밋하는 코드아무 폴더 (다운로드, 바탕화면, NAS)
지우기reset --hard와 clean은 실제 삭제휴지통으로만, 진짜 삭제는 사람만
되돌리는 단위커밋에이전트 작업 하나 (누가, 왜 했는지 기록)
큰 변경저장소 밖에서 리뷰정책을 넘으면 계획 → 사람 승인 → 적용

Description

  • 배경 Claude Code의 체크포인트는 에이전트가 직접 편집한 파일만 되돌림. 셸에서 실행한 rm, mv, git 밖 폴더(다운로드, 바탕화면)는 되돌릴 방법이 없음
  • 구현
    • 에이전트가 mv, rm 대신 MCP 도구(wasnew_move · wasnew_trash)를 부르면 원래 위치, 에이전트, 사유를 저널에 남김
    • 스냅샷(sha256), 이동 저널, 휴지통으로 작업 묶음 단위 되돌리기
    • 셸의 rm, mv는 선택형 훅(PreToolUse)이 막고 wasnew_trash를 쓰라고 돌려보냄. 승인 도구는 MCP에서 빼서 에이전트가 스스로 승인하지 못함
  • 검증
    • 사용자 파일을 지우지 않음. 진짜 삭제는 사람이 empty-trash 할 때만
    • 테스트 78개, CI 3개 OS × Node 2개 버전
  • 성과 이동 2,625건 2.9초, 같은 묶음 되돌리기 2.9초 (Linux 1대, 3회 중앙값)
  • 한계 훅은 명령 문자열만 보므로 스크립트 안에서 지우는 건 못 막음. 실제 Claude Desktop과 Claude Code에 붙인 사용은 아직 시험 전

    • KUKA KR210 기구학으로 타점마다 로봇이 닿는지 판정(관절 한계, 간섭, 접근 경로)
    • LightGBM 대리 모델이 같은 판정을 설계 1개당 0.05초에
  • 예시 설계안 A는 못 하는 타점 2개(S23, M00) → 플랜지만 넓힌 B도 2개 → 첫 타점 거리 80 mm, 실–B필러 간격 50 mm로 바꾼 C는 0개
  • 검증
    • 학습에 없던 설계 200개를 시뮬레이터와 대조. 첫 판 정밀도 93.4%에서 특징 계산 버그를 찾아 고친 뒤 100%
    • AI가 추천한 20안을 시뮬레이터로 다시 돌려 18안 일치, 틀린 2안은 경계 바로 옆
  • 설계 수정 에이전트
    • 「플랜지 폭은 그대로, 첫 타점 거리는 60 이하」 같은 요청을 LLM(qwen3.5 4B)이 제약으로 바꾸고, 후보 탐색 → 시뮬레이션 → 제출 도구를 불러 가장 적게 바꾼 설계를 찾음
    • 시뮬레이터가 못 하는 타점 0개를 확인한 설계만 제출 가능, 제약 위반은 코드가 거절
  • 성과
    • 1만 안 탐색 약 11시간 → 4.7분. AI는 1차 선별, 경계 근처는 시뮬레이터가 확정
    • 에이전트: 시작 설계 12개 전부 시뮬레이터 확인까지 성공, 실행당 평균 66초. 단변수 훑기만 주면 8/12였고 후보 탐색 도구를 준 뒤 12/12
  • 한계 변수 하나를 고정하면 에이전트 3/12, 전수 탐색 4/12. 제약 해석 12건 중 1건 틀림
